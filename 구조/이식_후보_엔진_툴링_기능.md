# 새 프로젝트 이식 후보: 엔진 / 툴링 기능 정리

> 작성일: 2026-04-28  
> 기준: `PROJECT_STRUCTURE.md`, `구조/프로젝트_구조_요약.md`, 실제 `Engine/`, `Editor/`, `AssimpTool/`, `Client/Bin/Resources/Data/MapTools/` 파일 확인  
> 목적: `Dx11_Naruto`에서 새 프로젝트로 옮길 가치가 있는 엔진 기능과 툴링 기능을 우선순위별로 정리

---

## 1. 결론

새 프로젝트로 이식 가치가 가장 큰 것은 **데이터/에셋 파이프라인**, **에디터 기반 제작 도구**, **엔진 직렬화/팩토리 기반 구조**다.

반대로 렌더러 전체, 플레이어/스킬/보스 전투 로직처럼 게임 고유성이 강한 코드는 그대로 이식하기보다 개념만 가져가는 편이 낫다.

---

## 2. 최우선 이식 후보

### 2.1 에셋 GUID / `.meta` 관리 시스템

| 항목 | 내용 |
|---|---|
| 추천도 | 매우 높음 |
| 이식 난이도 | 중간 |
| 핵심 위치 | `Engine/Public/Asset_Manager.h`, `Engine/Private/Asset_Manager.cpp` |
| 연동 위치 | `Client/Bin/Resources/`, `*.meta`, `.asset_cache.json` |

이식 가치:

- 파일 경로 대신 GUID로 에셋을 참조할 수 있다.
- 리소스 이동/이름 변경에 강한 구조를 만들 수 있다.
- 에디터의 에셋 피커, 프리팹, 이펙트, 모델 테이블과 연결하기 좋다.

이식 시 주의:

- 현재는 `Engine_Define.h`와 프로젝트 타입에 묶여 있으므로 `FAssetMeta`, `json`, `filesystem`, `stduuid` 의존성을 먼저 분리하는 게 좋다.
- 새 프로젝트에서는 `AssetDatabase` 또는 `AssetRegistry` 같은 독립 모듈 이름으로 빼는 편이 좋다.

### 2.2 프리팹 / GameObject 직렬화 구조

| 항목 | 내용 |
|---|---|
| 추천도 | 매우 높음 |
| 이식 난이도 | 중간~높음 |
| 핵심 위치 | `Engine/Public/Prefab_Manager.h`, `Engine/Private/Prefab_Manager.cpp` |
| 연동 위치 | `Engine/Public/GameObject.h`, `Engine/Public/Component.h`, `GameObject_Factory`, `Component_Factory` |

이식 가치:

- JSON 기반 프리팹 저장/로드가 가능하다.
- 컴포넌트 기반 오브젝트 구조를 새 프로젝트에서도 빠르게 구축할 수 있다.
- 에디터에서 만든 오브젝트를 런타임으로 넘기는 기본 통로가 된다.

이식 시 주의:

- 현재 `Protocol::OBJECT_TYPE`, `Protocol::ComponentID`에 의존한다.
- 새 프로젝트에서는 enum/protobuf 의존성을 걷어내고, 문자열 타입명 또는 자체 TypeID 레지스트리로 바꾸면 더 가볍다.
- `Transform`은 거의 필수 의존성이므로 같이 옮기거나 새 엔진의 Transform에 맞춰 어댑터를 만든다.

### 2.3 GameObject / Component / Factory 등록 시스템

| 항목 | 내용 |
|---|---|
| 추천도 | 높음 |
| 이식 난이도 | 중간 |
| 핵심 위치 | `Engine/Public/GameObject.h`, `Engine/Public/Component.h`, `Engine/Public/GameObject_Factory.h`, `Engine/Public/Component_Factory.h` |

이식 가치:

- 오브젝트 생성, 컴포넌트 부착, 에디터 생성 메뉴, 프리팹 역직렬화의 기반이다.
- `REGISTER_GAMEOBJECT_CATEGORY` 같은 등록 매크로가 에디터 분류와 잘 맞는다.
- 새 프로젝트 초기에 ECS까지 갈 필요 없이 실용적인 컴포넌트 구조를 만들 수 있다.

이식 시 주의:

- 현재는 DirectX `Device/DeviceContext`를 거의 모든 객체 생성자에 주입한다.
- 새 프로젝트에서는 렌더링 의존 객체와 순수 게임 객체를 분리하는 편이 좋다.
- `Protocol` enum 의존성 제거가 필요하다.

| 이식 난이도 | 낮음~중간 |
| 핵심 위치 | `Engine/Public/Reflection_Macro.h`, `Engine/Public/Property_Types.h` |

- 새 프로젝트에서는 `jsonKey`를 적극 사용해서 저장 포맷과 표시명을 분리하는 것이 좋다.

## 3. 툴링 최우선 이식 후보

### 3.1 Assimp 모델 변환 도구

| 항목 | 내용 |
|---|---|
| 추천도 | 매우 높음 |
| 이식 난이도 | 중간~높음 |
| 핵심 위치 | `AssimpTool/Public/Converter.h`, `AssimpTool/Private/Converter.cpp`, `AssimpTool/Default/BinaryWriter.cpp` |
| 출력 연동 | `Engine/Public/ModelBin_Types.h`, `Engine/Public/Model_BinaryLoader.h` |

이식 가치:

- Static/Skeletal mesh 변환, 머티리얼 JSON 출력, 애니메이션 bin 출력 흐름이 이미 있다.
- `.meshbin.meta`로 GUID까지 남기는 구조가 있어서 에셋 DB와 잘 맞는다.
- animation sidecar `.config`, `.props.txt` 처리까지 있어 DCC/FModel 계열 데이터 정리에 유용하다.

이식 시 주의:

- 현재 출력 포맷은 `FModelBinaryData`, `FMeshVertexAnimBin`, `FStaticMeshFileHeader` 등 프로젝트 타입에 묶여 있다.
- 새 프로젝트에서는 먼저 파일 포맷 스펙을 고정하고, `Converter`와 `Model_BinaryLoader`를 세트로 옮기는 게 좋다.

- `BakeCollisionSurfaceCache.py`처럼 런타임 최적화를 위한 바이너리 캐시 생성 도구가 있다.

## 6. 그대로 이식 비추천, 개념만 가져갈 것

### 6.1 게임 고유 스킬 / 보스 / 플레이어 FSM

볼 위치:

```text
Client/Public/Skill_*.h
Client/Public/PlayerState_*.h
Client/Public/Boss_Pain.h
Client/Public/BTTask_*.h
```

이식 비추천 이유:

- Naruto 액션 게임 전용 전투 규칙, 애니메이션, 이펙트, 입력, 리소스에 강하게 묶여 있다.
- 새 프로젝트에서는 상태 머신 구조, 데이터 드리븐 스킬 흐름, Notify 기반 타이밍 제어 개념만 가져가는 것이 좋다.

가져갈 개념:

- `StateMachine + SkillData + AnimationNotify + EffectAsset` 조합
- 스킬 시작/종료 시 이펙트 생명주기를 FSM에서 관리하는 원칙
- 루프 애니메이션의 Notify 중복 방지 규칙

## 8. 새 프로젝트용 권장 모듈 분리안

새 프로젝트에서는 현재 구조를 그대로 복사하기보다 아래처럼 모듈을 잘라내는 편이 좋다.

```text
Core/
  Base, Types, Json, Reflection, Command

Asset/
  AssetRegistry, MetaFile, GUID, AssetCache

Scene/
  GameObject, Component, Transform, Factory, Prefab

Render/
  Renderer, Shader, Texture, RenderTarget, Mesh, ModelLoader

Animation/
  Animation, AnimNotify, AnimNotifyState, NotifySerializer

VFX/
  EffectAsset, EffectComponent, Particle, Trail

AI/
  BehaviorTree, Blackboard, BTNode

Editor/
  EditorWindow, Inspector, Sequencer, AssetPicker, specialized views

Tools/
  AssimpConverter, DataTableConverter, MapPipeline, Packager
```

이렇게 나누면 `Dx11_Naruto`의 장점은 살리면서도, 현재 프로젝트의 `Protocol`, `Client`, `DirectX DeviceContext` 결합을 줄일 수 있다.

## 9. 한 줄 우선순위

가장 먼저 옮길 만한 것은 **`ConvertXLSX.py` → `CommandHistory` → `Reflection/Property` → `Asset_Manager` → `Prefab/Factory` → `AssimpTool + Model_BinaryLoader`** 순서다.

에디터 고급 기능은 그 뒤에 **Animation Notify, Cinematic, Effect Editor** 순서로 붙이면 새 프로젝트에서도 제작 효율을 크게 얻을 수 있다.
